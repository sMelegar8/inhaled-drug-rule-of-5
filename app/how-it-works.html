How the Inhalation SQL Workbench works

This page explains every process in the program, from data acquisition to the chart in the browser: what it does, why it is built this way, and what it shows. The numbers come from the build of 21 October 2026.

00

The business question

Lipinski's Rule of 5 describes oral drugs, which must be absorbed in the gut. An inhaled drug has a different goal: act in the lung and pass as little as possible into the rest of the body. There is no shared public rule for inhaled drugs.

The project question: are the chemical properties of approved inhaled drugs different from those of oral drugs, and how? The second step applies the findings to compounds active on PDE4, a respiratory target (for example in COPD).

Limitation

This is an exploratory analysis of public data. The database links 65 approved inhaled molecules against 1,249 oral ones: a small sample, to be presented as a hypothesis and not as a discovery.

In short

I took a rule that everyone uses and checked whether it also holds for inhaled drugs, which are at the core of many respiratory companies.

01

Data acquisition

src/01_download_data.py · output: data/raw/ + manifest.json

The program downloads two public sources and saves them without changing them:

  • ChEMBL (EMBL-EBI), release 37 of 1 May 2026: approved drugs with calculated properties, synonyms and ATC codes; IC50 and Ki measurements on human PDE4 and the compounds tested.
  • openFDA Drugs@FDA, export of 20 October 2026: FDA products with dosage form and route of administration. ChEMBL only has oral/parenteral/topical flags, so the inhaled route comes from here.

Why the API and not the full database

The full ChEMBL SQLite dump is 5.37 GB compressed and about 25 GB extracted, while the machine had 3.9 GB free. The program therefore queries the official API and downloads only the parts the question needs. It is a scoping choice: take the data you need, not all the data available.

How the code works

  • Pagination: the API returns at most 1,000 rows per page; the paginate() function follows the next link until there are no more.
  • Selected fields: the only= parameter requests only the useful columns and reduces the volume.
  • Retry with backoff: on network errors the program retries after 5, 10 and 20 seconds instead of failing.
  • Batches: the properties of the 7,326 PDE4 compounds are requested 100 at a time.
  • Manifest: for each file it records the URL, date and time, number of records and SHA-256 hash. If a file changes, the hash shows it.
In short

Every piece of data has a verifiable provenance: source, release, download date and file fingerprint. Anyone can rerun the analysis and check that they have the same inputs.

The data model

Empty columns

The ChEMBL 37 API does not return the descriptors calculated with ChemAxon (cx_logp, cx_logd, pKa, molecular_species): the schema declares them as always empty and they are left out of the analysis set. The charge of the molecule, important for inhaled drugs (for example the quaternary ammonium of tiotropium), will have to be calculated with RDKit.

Three design choices

  • Raw values kept. Measurements stay as published (published_value, published_units) next to the version standardised by ChEMBL. Cleaning happens later, in a visible way.
  • Documentation inside the schema. Every column has a comment in the SQL code; the app reads it and shows it in the "Database structure" panel.
  • Parents and salts. Many drugs exist as a salt (e.g. albuterol sulfate). Each molecule points to its parent_chembl_id, and properties are compared on the parent.
In short

I separated the entities, kept the original values and documented every column inside the schema itself, so the data dictionary never goes out of date.

03

Loading and integrating the sources

src/02_build_database.py · output: data/processed/pharma_inhalation.sqlite (25.3 MB)

The script rebuilds the database from scratch on every run: it deletes the file, runs schema.sql, and loads the JSON files and the FDA file. Rebuilding from scratch guarantees that the result depends only on the raw files and the code.

The integration problem: linking FDA and ChEMBL

FDA and ChEMBL do not share an identifier. The only link is the name of the active ingredient, written in different ways. The script solves it in two passes:

  1. Exact match of the FDA name with the ChEMBL preferred name or a synonym (after normalising case and spaces). Example: ALBUTEROL SULFATE finds the salt molecule, which points to the parent CHEMBL714.
  2. If that fails, counter-ions and hydrates are removed from the end of the name (SULFATE, HYDROCHLORIDE, MONOHYDRATE…) and the search is repeated.

Each row records the method used (match_method), so the link can be checked:

MethodFDA namesShare

What is left out

The 215 unlinked names are mostly combinations written in a single field ("ABACAVIR, DOLUTEGRAVIR, LAMIVUDINE"), biologics with a suffix ("AFLIBERCEPT-BOAV") and very recent drugs. For the question about small-molecule inhaled drugs the impact is limited, but it should be measured before the final analysis.

A materialised view for speed

The view v_molecule_routes holds the join rule: products → active ingredients → map → parent molecule, grouped by route. Recomputing it in the browser on every query took about 5.4 seconds. The script computes it once and saves it in the indexed table molecule_routes: the same query drops to about 0.2 seconds.

In short

92% of the names link exactly. For the others I know exactly which ones they are and why they do not link, and every link is traced.

04

Distributing the database

app/pharma_inhalation.sqlite.gz.b64.txt (9.3 MB)

The app runs entirely in the browser, with no server. To ship the database with it, the script compresses it with gzip (25.3 MB → 7.0 MB) and encodes it in base64, a text format that any static host serves. The browser does the reverse: it decodes the base64, decompresses with the native DecompressionStream API and opens the file.

In short

Whoever opens the link installs nothing: the database and the SQL engine arrive with the page.

05

Exploration: SQL, charts and schema

app/index.html · app/stats.js · libraries: sql.js 1.10.3, Plotly 2.35.2 (strict build)

The SQL engine

sql.js is SQLite compiled to JavaScript. The database is loaded in memory, so queries are real SQLite queries, with JOIN, GROUP BY, subqueries and functions. Changes (CREATE, UPDATE) last only for the session and do not touch the original file.

From query to chart, automatically

  1. The query returns columns and rows; the table shows the first 1,000 rows, sortable.
  2. Type inference: a column is numeric if all non-null values are numbers; for the others the distinct values are counted.
  3. Axis choice: a scatter plot uses the first two numeric columns, a histogram the first one, and a box plot groups by a text column with 2-12 values. If the previously chosen column still exists, the selection is kept.
  4. Groups and colours: the 7 largest groups get a colour and the rest go into "Other". The same value (for example INHALATION) keeps the same colour from one query to the next. The palette is checked for colour blindness.
  5. Missing values: rows without a numeric value are not drawn, and the chart states how many were excluded.

The database structure

The left-hand panel reads the tables from sqlite_master, the columns from PRAGMA table_info and the descriptions from the comments in the schema. The search filters tables and columns by name or description; clicking a column inserts it into the query.

Statistical analysis on the filtered result

The "Statistical analysis" panel works on the rows returned by the query, so the filter is the WHERE clause. You choose the numeric variables and, if needed, a group column. Four analyses:

  • Descriptive: n, missing values, mean, standard deviation and quartiles, per variable and per group.
  • Correlations: Pearson or Spearman matrix (on ranks, more robust to skew and extreme values) as a heatmap, plus the list of pairs sorted by strength. Each pair uses the rows where both values exist.
  • PCA: reduces many correlated properties to a few components. Variables are standardised (z-score), so molecular weight and the number of H-bond donors count equally. The app shows the explained variance (scree plot), the scores coloured by group with the variable vectors (biplot) and the loading table. The scores can be saved to the pca_scores table and queried with SQL.
  • Group comparison: Mann-Whitney for two groups, Kruskal-Wallis for three or more. These are non-parametric tests: they do not assume normal distributions, which these properties do not follow. P-values are corrected for multiple testing with the Holm method, and each test reports an effect size (rank-biserial r or ε²) with its threshold.

Example on the clean data, 46 inhaled against 1,108 oral drugs: inhaled drugs have more H-bond donors (median 3.5 against 2, medium effect) and a lower QED. In the PCA on 8 descriptors, excluding the molecules that also exist as oral products, the first component explains 46.8% of the variance, and the first two together 72.5%.

How I know the calculations are right

The calculations live in a separate file, app/stats.js. The script tests/validate_stats.py runs it with Node on the same data and compares every result with numpy, pandas and scipy: 40 checks, from descriptive statistics to PCA loadings. The largest differences are of the order of 10⁻¹⁴ for exact calculations and 10⁻⁷ relative for p-values. The check runs automatically on GitHub at every change.

In short

I built the tool I use to explore the data: every hypothesis becomes a query, and every query immediately becomes a chart and a test. And I checked the tool's calculations against the standard scientific libraries.

06

Data cleaning and the exclusion ledger

src/cleaning.py · notebooks/02_data_cleaning.ipynb · output: 6 new tables + reports/cleaning_log.csv

Cleaning is a series of decisions. The program makes them explicit, ordered and countable:

  • Raw tables do not change: the result goes into new tables (activities_clean, activity_potency, molecule_routes_clean, inhalation_dataset).
  • Rules are applied in sequence and each one only sees what is left by the previous ones: every excluded record has exactly one reason.
  • A Python object, the Ledger, records for each rule the rows before, removed, after and flagged, plus the identifier of every excluded record. It ends up in the cleaning_log and cleaning_exclusions tables, which the app can query with SQL.
  • The logic lives in a reusable Python module; the notebook runs it step by step with the evidence (tables, charts, checks).

Part A · PDE4 activity measurements: from 11,954 to 8,793

RuleReasonExcluded
A1 · Flagged by curatorsChEMBL marks the value as suspect259
A2 · Relation other than "="Censored values (<, >) only give a threshold, not a potency2,892
A3 · Unit other than nMPercentages and missing units cannot become concentrations10
A4 · Missing value or ≤ 0The logarithm needs a positive number0
A5 · pX outside 3-12Weaker than 1 mM or stronger than 1 pM is almost always a unit error0

Each measurement becomes a logarithm: pX = 9 − log10(value in nM). On a log scale, values from picomolar to millimolar become comparable, and one unit means a factor of 10.

  • Check A6: the calculated pX matches the pChEMBL value calculated by ChEMBL in all 8,793 measurements (0 differences above 0.05). Two independent routes, same number.
  • Aggregation A7: repeated measurements become one median per molecule × target × measurement type: 6,887 pairs. The median is more robust to outliers than the mean.
  • Check A8: 208 pairs have replicates that differ more than 10-fold. They stay in the data, flagged with inconsistent = 1.

Part B · Analysis set: from 1,305 molecules to 46 inhaled + 1,108 oral

First, three transformations that exclude nothing but fix the way the data is written:

  • Normalised routes of administration: "INHALATION, ORAL" and "Inhalation, Oral" are split and upper-cased. Inhaled molecules go from 65 to 66.
  • ATC codes inherited from salts: many ATC codes are stored on the salt (e.g. tiotropium bromide, R03BB04) and are assigned to the parent molecule.
  • Exclusive groups: a molecule with inhaled products goes into the inhaled group even if it also exists as an oral product (15 cases, flagged with also_oral for the sensitivity analysis).

Then six exclusion rules, with a symmetrical logic between the two groups:

RuleExamplesExcluded
M1 · Not a small moleculeinhaled insulin, radiopharmaceuticals37
M2 · Core properties missingsodium chloride, noble gases63
M3 · Medical gases (< 100 Da or ATC V03AN)oxygen, nitrogen, nitric oxide, nitrous oxide10
M4 · Diagnostics only (ATC V04/V08/V09)methacholine, contrast agents12
M5 · Inhaled drugs acting on the nervous system (ATC N)sevoflurane, isoflurane, loxapine, levodopa9
M6 · Oral drugs acting only in the gut (ATC A06/A07)mesalazine, loperamide, lactulose20

M5 and M6 are the central choice. An inhaled anaesthetic must reach the blood, the opposite of a drug that must stay in the lung; an oral drug acting in the gut is designed not to be absorbed, the opposite of a systemic oral drug. Keeping them would blur exactly the difference we want to measure.

Automatic checks

  • References: albuterol, budesonide, fluticasone propionate, formoterol, ipratropium, salmeterol and tiotropium must be in the inhaled group. If a rule removed them, the notebook stops with an error.
  • Integrity: kept records + excluded records = starting records, and the recorded exclusions match the sum in the ledger. Here too the notebook stops if the numbers do not add up.
Limitation

Rules M3-M6 use the ATC classification as an indicator of therapeutic intent. It is an approximation: 7 inhaled drugs without an ATC code (including arformoterol, vilanterol and ensifentrine) stay in the group without this filter. Among them, pentetic acid (DTPA), a chelator that acts systemically, should be reviewed by hand.

In short

The inhaled group has 46 molecules, not 66. I can say exactly which 20 I removed, with which rule and why, and the notebook proves that the reference drugs are all still there.

Questions a reviewer might ask

Why SQLite and not a database server?

For a 25 MB dataset SQLite is enough: one file, no installation, standard SQL. The schema moves to PostgreSQL without substantial changes if the data grows.

How do you make sure the data is the right data?

Every raw file has its source, date, number of records and SHA-256 hash in the manifest, and the same values are in the dataset_info table. The database can be rebuilt from scratch with two commands.

Why does your inhaled group exclude some inhaled drugs?

Because the question is about drugs that must act in the lung. Medical gases, volatile anaesthetics and drugs inhaled to reach the brain have the opposite goal. The 20 exclusions are listed one by one, with the rule that removed them, in the cleaning_exclusions table.

Why didn't you clean the data while loading it?

Because cleaning is a series of decisions that need to be justified. Keeping the original values, I can show how many rows each rule removes and why, and change a rule without downloading anything again.

How reliable is the FDA-ChEMBL link?

92.3% of the names link exactly, 0.3% after removing the salt, and 7.4% remain excluded. Each row states its method, so the error is measurable and can be spot-checked.

What does this analysis not show?

It does not prove that a molecule works by inhalation. It describes the differences between drugs already approved for inhaled and oral use; with 65 inhaled molecules the results are indications to be validated.
